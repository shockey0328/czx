# 学科网数仓表检索与 SQL 生成

## 适用场景

- 根据自然语言查找用户、内容、交易、财务、日志等主题的数仓表。
- 为明确的分析需求推荐主表、维表和关联关系。
- 在实时 schema 核验后生成 MaxCompute SQL。
- 判断现有聚合表是否足够，避免无必要地回退到明细层重复聚合。

## 知识库结构与权威性

当前知识库以 `knowledge/tables/` 为唯一的本地检索入口，按数仓层级组织：

```text
knowledge/tables/
├── bi/    # BI 报表与主题统计结果
├── ads/   # 面向业务应用和报表的汇总结果
├── dwd/   # 明细数据
└── dim/   # 维度与属性补充
```

每个表文件通常包含以下信息：表名、层级、本地描述、主题标签、数据粒度、分区字段、关键字段、字段说明、ETL 提示、使用边界和数据质量提示。

**强制规则：**

1. 每次找表、写 SQL 或数据分析请求，必须先检索 `knowledge/tables/` 下的本地表文件。
2. 在读取并筛选本地候选表之前，禁止使用 `mcp__maxcompute__list_tables`、`mcp__maxcompute__search_meta_data` 等全量发现工具。
3. 本地 Markdown 只用于候选发现和语义判断；字段名、类型、分区和 SQL 表引用必须以实时 `mcp__maxcompute__get_table_schema` 结果为准。
4. 如果知识库中没有匹配表，明确说明未找到本地候选，再询问是否允许扩大元数据搜索范围。

## 表选择优先级

用户没有指定层级时，按以下顺序筛选：

1. **`bi`**：已有主题指标或报表结果时优先，通常可直接分析。
2. **`ads`**：业务应用和报表汇总表，适合明确业务场景的指标分析。
3. **`dwd`**：只有上层表缺少所需字段、粒度不匹配，或确实需要明细事件时使用。
4. **`dim`**：用于补充用户、资源、题目、产品等属性，不作为分析主表，除非用户明确要求维度数据。

本技能当前知识库没有独立维护“常用表”清单，因此不要虚构或默认常用表优先级。若用户明确指定层级，则以用户指定为准。


- **主题匹配**：表名、描述和主题标签是否覆盖用户意图。
- **粒度匹配**：用户级、资源级、订单级、事件级或日/月级是否一致。
- **指标覆盖**：关键字段和已有聚合指标是否满足需求。
- **时间粒度**：日、月、全量快照或累计表是否符合需求。
- **数据质量**：关注文件中的数据质量提示，必要时在回答中说明限制。

知识库字段可能被 ETL SQL、模板变量（如 `${dt}`）或截断内容污染。若“数据粒度”“分区字段”“关键字段”包含 SQL 关键字、模板变量、括号不闭合或明显无法解析的片段，标记为“本地元数据不可靠”，不得据此推断粒度、指标或分区；只能将其作为弱候选信号，并依赖实时 schema 与业务确认。

不要仅凭 `_1d`、`_1m`、`_td`、`_df` 等后缀判断相关性；后缀只用于辅助判断时间粒度。

## 语义关键词

按表名、描述、主题标签和关键字段综合匹配，不要只做字符串命中：

| 业务主题 | 优先关注关键词 |
|---|---|
| 用户、会员、账号 | `user`, `member`, `mbr`, `account`, `creator` |
| 交易、订单、支付 | `trd`, `trade`, `order`, `payment`, `pay`, `iap`, `revenue`, `moneyrecord` |
| 内容、资源、题目、试卷 | `cont`, `content`, `resource`, `res`, `paper`, `question`, `document`, `course` |
| 财务、资产、成本 | `fin`, `finance`, `asset`, `cost`, `revenue`, `share`, `salary`, `reward` |
| 日志、行为、下载、消费 | `log`, `event`, `action`, `download`, `consume`, `feedback` |
| 学校、组织、学段、学科、产品 | `school`, `stage`, `subject`, `product`, `course` |
| AI、批改、任务、策略 | `ai`, `aigc`, `grading`, `task`, `policy` |
| 统计结果 | `stats`, `stat`, `rate`, `reten`, `profile` |

同一张表同时覆盖多个主题时优先推荐；例如交易+会员表适合会员收入分析，用户+日志表适合行为分析。主题相同的候选表超过 3 张时，按粒度、时间周期和字段覆盖进一步缩小范围。

## 时间后缀参考

| 后缀 | 常见含义 | 使用提示 |
|---|---|---|
| `_1d` / `_di` | 日统计或日增量 | 适合按天趋势和日明细 |
| `_1m` / `_mi` | 月统计或月增量 | 适合月度指标，核对实际粒度 |
| `_td` | 截至当前的累计结果 | 适合累计口径，注意重复统计 |
| `_df` | 常见表示全量或快照结果 | 是否按日、是否有分区必须以文件和实时 schema 为准 |
| `_di` / `_mi` | 具体含义依表定义 | 不能仅凭后缀推断增量或快照 |
| `p_dt`、`order_month`、`mth` 等 | 可能是分区字段或业务日期 | 必须以实时 schema 的分区键定义为准 |

知识库中的“数据粒度”优先于文件后缀。若粒度描述异常、被 ETL 片段污染或与需求冲突，必须用实时 schema 和用户口径进一步确认。

## 标准工作流程

1. **判断意图**：区分找表、写 SQL、指标分析或需要 HTML 报告。
2. **提取需求**：识别业务主题、目标指标、主体粒度、时间范围、分组维度和过滤条件。
3. **检索本地知识库**：在 `knowledge/tables/bi`、`ads`、`dwd`、`dim` 中按优先级和语义匹配候选文件；先看文件顶部的描述、标签、粒度、分区和关键字段，再阅读相关字段与 ETL 提示。
4. **推荐候选**：通常给出 1 张主表和 0-2 张补充表，说明选择理由、层级、粒度、时间粒度和关键字段。不要为了凑数量列出无关表。
5. **核验实时元数据**：对最终候选调用 `mcp__maxcompute__get_table_schema`，确认字段、类型、分区键、项目和 `sqlTableRef`；需要判断可用分区时再调用 `mcp__maxcompute__get_partition_info`。
6. **生成 SQL**：只使用实时 schema 确认过的字段和 `sqlTableRef`，添加必要的分区过滤，并避免无界查询。
7. **处理歧义**：如果主体、指标口径、时间范围或层级不明确，先列出候选和需要确认的问题，不直接编造 SQL。
8. **扩展分析**：用户要求生成可视化或 HTML 报告时，先完成本技能的表检索和 schema 核验，再调用 `edw-data-analysis`。

## 项目与 MaxCompute MCP 规则

### 表项目映射

知识库表文件给出的默认项目映射为：

- `bi`、`ads`：知识库常见推荐项目为 `dmp_ads`，但这只是候选提示，不代表当前环境的实际项目。
- `dwd`、`dim`：知识库常见推荐项目为 `dmp_cdm`，但这只是候选提示，不代表当前环境的实际项目。

项目解析顺序必须是：调用方明确指定的实际项目和 schema > 实时工具配置/返回结果 > 知识库中的“推荐项目”提示。数仓层级不是 schema；知识库也没有为每张表提供可直接执行的 schema。若实际项目或 schema 任一缺失，先询问或停止 schema 核验，不得把 `bi`、`ads`、`dwd`、`dim` 当作 schema，也不得编造项目名。

### SQL 提交与表引用

- 调用 `mcp__maxcompute__get_table_schema` 前，必须明确传入 `project`、`schema` 和 `table`；不要把层级名当作 schema，也不要把提交项目当成数据所在项目。
- `get_table_schema` 查到表后，必须记录其返回的 `sqlTableRef`、实际项目、字段和分区信息。若表不存在、项目不匹配或没有可用的 `sqlTableRef`，停止生成 SQL 并说明原因。
- 调用 `mcp__maxcompute__execute_sql` 时，提交项目统一使用 `project="dmp_analyst"`。
- SQL 中的表名必须使用 `get_table_schema` 返回的 `sqlTableRef`，不要自行猜测两级或三级命名。
- 跨项目查询时，按照实时 schema 返回的引用格式书写；不要把提交项目 `dmp_analyst` 误当成数据所在项目。
- 不要通过 SQL 中的 `SET` 修改只读或安全配置；执行工具会强制只读。
- 执行前估算成本或设置合理的 `maxCU`，尤其是 dwd 明细表查询。
- 分区表必须在 `WHERE` 中过滤实时 schema 返回的全部必要分区字段；先用 `get_partition_info` 确认分区格式，不要默认所有表都只有 `dt`。
- 用户未提供必要分区值时，只有在能依据实时元数据和用户时间范围安全推导时才自动补充；否则先询问，禁止用普通字段过滤替代分区过滤。
- SQL 只选择需要的字段，开发验证时添加 `LIMIT`，避免 `SELECT *` 和全表扫描。

## 输出要求

### 找表

列出最多 3 张候选表，每张包含：

- 表名和层级。
- 主题、粒度和时间周期。
- 命中的业务语义。
- 推荐理由和主要限制。
- 是否需要关联维表或实时 schema 核验。

### 写 SQL

先说明主表及其选择理由，再给出 SQL。SQL 上方使用：

```sql
/* 推荐原因：说明主表、粒度和为何满足需求 */
```

同时注明：

- 实际引用的 `sqlTableRef`。
- 关键字段和指标口径。
- 分区过滤条件。
- 维表关联键、去重方式和可能的重复计数风险。

### 数据分析

先说明指标口径、分析粒度、时间范围和候选表，再给出可执行 SQL。若本地知识库缺少字段或口径无法确认，应明确标注“需要实时 schema/业务确认”，不要臆测。

## 使用边界

- 本地知识库是表发现和语义检索资料，不替代实时元数据。
- ETL 片段和字段说明可能不完整或存在脏数据；不能据此推断未核验的字段。
- 不要为了满足层级优先级而使用粒度不匹配的聚合表。
- 上层聚合表已经提供目标指标时，不要回退到 dwd 重新聚合，除非需要明细或必须重算口径。
- 涉及用户输入、动态表名或外部参数时，先做边界校验；不要将未经验证的内容直接拼接到 SQL。
- SQL 查询应遵守数据权限和最小字段原则；不要输出不必要的敏感字段。
