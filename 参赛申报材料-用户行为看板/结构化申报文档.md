# 参赛思路

本项目要解决橙子学与学伴场景下的用户个案行为分析问题。产品、运营、教研在处理客诉、流失、转化卡点或改版验证时，往往已经拿到具体用户 ID，却很难从海量埋点里快速还原路径。本看板定位为用户个案放大镜：按用户 ID 与日期拉取真实行为明细，并用 AI 生成可读报告。它不是整体 UV 或留存大盘；核心数据等汇总看板不在本申报范围内。

在线入口：https://d1.fuxue.work/ （周度选择用户行为），也可打开 https://d1.fuxue.work/user-behavior.html 。完整取数与 AI 分析依赖后端服务；公网说明页会引导至内网服务地址（需公司网络或 VPN，配置见 intranet-user-behavior.json）。

参赛方式突出三条主线：一是按用户取数（橙子学 czx 与学伴 xueban 相关埋点）；二是 AI 双模式解读（常规四段式全景复盘，以及针对流失、卡点、转化等的问题深挖）；三是可运营的数据链路（数仓按日导出发布、本机索引，或内网 MCP 按需查询）。

演示路径：打开 https://d1.fuxue.work/ 进入用户行为，确认数据可用范围，选择不超过 7 天的日期，填写数字用户 ID，先做常规性分析查看轨迹与卡点，再做针对性分析追问具体问题，最后说明数据更新与服务部署方式。

预期成果：可分享的个案行为分析能力；把翻原始日志变为选日期、填 ID、问一句；形成取数、解读、复盘同步的闭环；沉淀使用说明、更新 SOP、导出脚本与工具包，供其他需要个案复盘的业务线复用。

# 问题说明

当前流程与协作中的主要痛点如下。

痛点一：埋点体量大，人工翻日志成本极高。橙子学与学伴单日日志可达数十万至近两百万行量级，业务同学无法在 Excel 里按用户高效检索。影响产品、运营、教研处理工单与专项复盘的时效。

痛点二：已知用户 ID 仍难还原完整路径。客服或后台能提供 ID，但缺少按用户加日期的一站式查询与时间线呈现，导致反馈与真实行为对不齐。影响问题定位准确率与跨角色沟通效率。

痛点三：有明细不等于有结论。即便导出部分日志，仍需人工翻译页面、点击与中断含义，结论依赖少数熟手，难沉淀、难交接。影响复盘深度与新人上手速度。

痛点四：大盘指标无法回答个案为什么。核心数据、搜索等汇总看板能发现问题人群或异常周，但无法解释某个用户卡在哪一步。影响从发现到归因的闭环。

痛点五：数据接入与服务形态不统一时难稳定交付。实时全量查询不适合公网 Serverless；本地 Excel、索引库、数仓导出若缺少标准流程，易出现缺数、截断或服务不可达。影响可信度与持续运维成本。

# 方案说明

总体方案采用按用户查询的行为服务，加上 AI 解读，再加上可运维的数据发布链路。

产品侧提供日期筛选、用户 ID 输入（支持英文逗号多 ID）、常规与针对性分析模式，以及小橙子对话式报告界面。数据侧支持三种形态：数仓按日导出 JSON 后经云存储或 Release 供线上读取；本机按日分片 JSON 加用户与日期双重索引；内网环境下 DATA_SOURCE 为 warehouse 时通过 MCP 按用户实时取数。明确约束：不要在公网 Serverless 上对全量做实时 MCP。

AI 侧使用 DeepSeek，密钥走环境变量 DEEPSEEK_API_KEY。常规性分析输出四段：用户完整行为轨迹、使用习惯与特征、产品问题与体验卡点、产品与运营优化建议。针对性分析按问题定位、原因分析、数据支撑、解决建议组织。只写有日志依据的内容，不编造，不输出原始埋点大表。

工程侧主要位于用户行为看板周度目录，包括 server-with-db.js、db-manager、导出脚本 export-from-warehouse.js、分析与取数 API，以及门户跳转页 user-behavior.html 与 intranet-user-behavior.json。统一门户入口为 https://d1.fuxue.work/ 。

关键实现步骤：一是明确个案场景与字段（时间、用户、页面、元素、事件、来源、平台等）；二是建立按日存储与按用户查询能力；三是对接数仓导出或 MCP；四是接入常规与针对性两套 AI Prompt；五是接入门户并配置内网地址；六是用真实用户 ID 做抽检与业务试用。详细 SOP 与工具包见成果附件。

# 效果说明

以下以流程可验证结果为主；不编造具体用户行为或经营数字。可用处理一次客诉或个案复盘做前后对照计时。

效率方面：由在海量 Excel 或原始日志中人工筛选，变为输入用户 ID 与日期后秒级或更快取出行为明细；由人工翻译埋点，变为 AI 生成结构化报告并可追问；由汇总看板发现异常后无法下钻，变为可对具体用户完成归因验证。验证方式包括：同一用户同一日期能否稳定查出记录；常规报告是否具备四段结构；针对性问题是否围绕提问作答。

质量方面：结论绑定真实埋点与记录条数提示，降低凭印象复盘；常规与针对性模式匹配不同问题成熟度；查无数据时明确提示，不用假轨迹顶替。业务上可支撑产品验卡点、运营看流失停点、教研看找卷与练习路径等场景。

成本与协作方面：减少熟手加班翻日志；使用说明降低分享与培训成本；导出加发布 SOP 降低每次从零搭环境的成本。已可演示：门户可进入用户行为；支持常规与针对性分析；具备数仓导出、本地索引与内网服务等多种数据形态。

边界需同时说明：必须先有数字用户 ID；建议单次日期范围不超过 7 天；AI 为辅助解读，关键决策需人工复核；完整服务在内网场景需网络可达。

# 复用说明

本项目可沉淀并推广的资产如下。

可沉淀模板：个案分析页信息架构（日期、用户 ID、分析模式、对话报告）；常规四段式报告模板；针对性四步分析模板；提问话术库（路径复盘、流失、卡点、转化、找卷练习等）。

可沉淀 SOP：数仓单日试导出到区间导出再到云端发布；内网 MCP 服务启动与 intranet-user-behavior.json 配置；Excel 历史导入与 db-manager 抽检；业务侧三分钟上手流程。完整步骤见成果附件中的用户行为看板更新 SOP。

可沉淀工具包：导出脚本 scripts/export-from-warehouse.js；本地索引与查询 db-manager.js；分析与取数 API；使用说明.md 业务分享文档；门户跳转与内网地址配置。

可推广团队与场景：产品用于反馈复盘、改版验证、转化漏斗个案；运营用于高价值或沉默用户、流失召回；教研用于找卷、预览、练习与学伴衔接路径观察；客服与产研协作用于工单对齐真实行为时间线；其他业务线可复用按用户取数加 AI 双模式框架，替换为本业务埋点表。

最小落地包建议先交付五样：可按用户加日期查询的服务与页面；常规与针对性两套 Prompt；一份数据更新 SOP；一份面向业务的使用说明；一个可分享的入口（门户或独立服务地址）。
